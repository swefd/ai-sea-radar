# Налаштування знімка: вікно збору, клас B, скасування, діагностика — проєктне рішення

**Дата:** 2026-09-29. **Гілка:** `worktree-snapshot-settings` від `main` (5820048).
**Підстава:** `docs/IMPROVEMENTS.md`, П-1…П-3. Замовник (власник проєкту) погодив
у розмові всі три покращення зі змінами, записаними нижче, і додав кнопку
«Скасувати». Цей документ — єдине місце, де записані нові узгоджені значення;
`docs/tasks/SPRINT-02.md` — документ замовника й не правиться.

## 1. Що погоджено

| Нове | Кнопка **«Скасувати»** під час завантаження; після неї — окремий стан «скасовано» |

## 2. Межі, що не змінюються

- **Налаштування не зберігаються між запусками** (`PROJECT_BRIEF.md:113` виключає
  назавжди). Жодного `localStorage`, cookie чи сесії: після оновлення сторінки —
  15 с і клас B вимкнено.
- **Без параметрів поведінка дослівно як у R2** (`PROJECT_BRIEF.md:47` — «без
  налаштування»). Наявні тести R2 лишаються зеленими без змін.
- **Сирий текст помилки провайдера ніде не показується** — ні в `message`, ні в
  діагностиці, ні в консолі.
- **Скасування не повертає частковий набір суден** (`SPRINT-02.md:28`).
- **Правило «результат останньої спроби»** (`SPRINT-03.md:77`) не змінюється:
  скасована спроба — теж спроба, з результатом «скасовано».
- Ліміт 100 суден, район, типи значків і картка — без змін.
- Нових залежностей немає.

## 3. Контракт `GET /api/snapshot`

### 3.1 Параметри запиту

| Параметр | Допустимі значення | Без параметра |
|---|---|---|
| `window` | точно одне з `15, 30, 60, 120, 180, 240, 300` (десятковий рядок без знаку й нулів попереду) | `15` |
| `classB` | `0` або `1` | `0` |

Будь-яке інше значення (зокрема `14`, `16`, `99999`, `abc`, порожній рядок,
`classB=2`, повтор параметра) → **HTTP 400**:

```json
{ "ok": false, "attemptedAt": "<ISO>", "error": { "code": "invalid_params", "message": "Некоректні параметри запиту" } }
```

Перевірка — до читання ключа: некоректний запит не торкається ні ключа, ні
мережі. Невідомі інші параметри ігноруються.

### 3.2 Відповідь

Успіх (200) — поточна форма плюс два поля; `windowSeconds` тепер — **застосоване**
вікно, а не константа:

```ts
{
  ok: true, vessels, collectedAt, windowSeconds, count, truncated, reason,
  includeClassB: boolean,
  diagnostics: SnapshotDiagnostics,
}
```

Помилка (502 для кодів R2, 400 для `invalid_params`):

```ts
{ ok: false, attemptedAt, error: { code, message }, diagnostics: SnapshotDiagnostics | null }
```

`diagnostics` = `null` для `no_api_key` та `invalid_params` (до збору справа не
дійшла). Для решти помилок — лічильники на момент завершення; суден у помилці
немає.

```ts
type SnapshotDiagnostics = {
  connectMs: number | null;   // від старту до onOpen; null — з'єднання не відкрилося
  messages: number;           // усі повідомлення з даними, крім підтвердження підписки
  rejected: number;           // повідомлення, які перетворювач повернув null
  byType: Record<string, number>; // MessageType → кількість (з messages)
};
```

`byType` рахує лише типи, що справді прийшли. Ключ — `MessageType`, але **лише
з білого списку** `PositionReport`, `StandardClassBPositionReport`; будь-яке
інше значення, відсутнє поле й битий JSON — під ключем `other`. _Уточнення при
плануванні:_ `MessageType` — рядок провайдера, а сирий текст провайдера на
екран не потрапляє (§2); довільний ключ був би саме таким текстом. Битий JSON
рахується в `messages`, `rejected` і `other`.

`SnapshotErrorCode` доповнюється `'invalid_params'`.

### 3.3 Узгоджені значення — одне місце

`src/shared/config/aisstream.ts`:

- `SNAPSHOT_WINDOW_OPTIONS = [15, 30, 60, 120, 180, 240, 300] as const`
- `SNAPSHOT_WINDOW_SECONDS = 15` — типове, як і було; тест стереже, що воно
  входить до `SNAPSHOT_WINDOW_OPTIONS`
- `SNAPSHOT_VESSEL_LIMIT = 100` — без змін

Тексти (`'Некоректні параметри запиту'`, `'Завантаження скасовано'`, підписи
інтерфейсу) живуть поруч з наявними текстами тих самих модулів.

## 4. Сервер

- **Розбір параметрів** — чиста функція
  `parseSnapshotParams(searchParams: URLSearchParams)` →
  `{ windowSeconds, includeClassB } | null`, у `src/_app/api-routes/`, поруч з
  обробником.
- **Підписка.** `buildSubscription(apiKey, { includeClassB })`:
  `FilterMessageTypes` = `['PositionReport']` або
  `['PositionReport', 'StandardClassBPositionReport']`. Без опцій — як зараз.
- **Збирач.** Отримує `windowMs` із запиту. Рахує `diagnostics` і повертає їх у
  **обох** гілках `CollectResult`. Скасування клієнтом — наявний `request.signal`
  → `onAbort` → прибирання; код, що при цьому повертається, клієнт уже не читає.
- **Перетворювач.** Розбирає `Message.PositionReport` і
  `Message.StandardClassBPositionReport` за тими самими правилами валідації
  (`SPRINT-02.md:27`). Регістр і набір полів класу B — лише за живим зразком
  (§6).

## 5. Інтерфейс

### 5.1 Панель, згори вниз

1. **Повзунок** «Вікно збору: 60 с» — `<input type="range" min=0 max=6 step=1>`
   над індексами `SNAPSHOT_WINDOW_OPTIONS`; під ним мітки `15 с · 30 с · 60 с ·
   2 хв · 3 хв · 4 хв · 5 хв`; `aria-valuetext` — «60 секунд».
2. **Прапорець** «Малі судна (клас B)».
3. **Кнопка** «Завантажити справжні позиції»; під час `loading` та сама кнопка
   стає **«Скасувати»** — одна кнопка, а не дві. _Рішення власника 2026-10-02_
   (план пропонував дві кнопки з заблокованою «Завантажити»; власник обрав одну).
   Це **змінює контракт R2** `SPRINT-02.md:31` «кнопка заблокована»: у `loading`
   кнопки завантаження немає, тож «удруге натиснути не можна» тримається тим,
   що її нема, а не `disabled`. Другий клік подвійного кліку (`detail > 1`)
   спробу не скасовує — інакше подвійний клік по «Завантажити» обривав би
   власний запит.
4. Підпис (наявний) + кнопка згортання.
5. Повідомлення `role="status"` (наявне).
6. **«Докладно»** — `<details>`, закритий за замовчуванням.
7. Картка.

Під час `loading` повзунок і прапорець `disabled`. Згорнута панель лишає видимими
пункти 1–5 так само, як зараз лишає кнопку й підпис; «Докладно» ховається разом
із тілом.

### 5.2 Стани

`LoadState` = `idle-demo | loading | success | error | cancelled`.

- Кожна спроба має власний `AbortController` (у `ref`, не в стані: він нічого
  не рендерить); розмонтування компонента обриває запит. Відповідь спроби, чий
  контролер уже скасовано, ігнорується — пізня відповідь не перезаписує
  «скасовано» чи наступну спробу.
- `cancelled`: суден немає, вибір і картка прибрані, підпис «Даних на карті
  немає», повідомлення «Завантаження скасовано», блоку «Докладно» немає.
- `fetchSnapshot(params, signal)` → `SnapshotResponse | 'cancelled' | null`.
  Скасування — окремий результат, а не `null`, тому не стає помилкою «Немає
  відповіді сервера».

### 5.3 Підпис

Наявний текст дослівно, число — з `windowSeconds` відповіді, **завжди в
секундах**: «AISStream · знімок за 120 с · отримано … · суден: N · вибірка
неповна». Якщо `includeClassB` — у кінець « · із малими суднами (клас B)»;
«· зупинено на ліміті 100» — перед ним.

### 5.4 «Докладно»

Показується в `success`, `empty`, `error`, коли `diagnostics !== null`. Один рядок:

«з'єднання: 0,2 с · повідомлень: 11 (PositionReport: 11) · відкинуто: 0 · суден: 4»

Для `connectMs === null` — «з'єднання: не відкрито». «суден» — лише в успіху.
Секунди з однією десятковою й комою. Форматування — чиста функція поруч із
`snapshot-caption.ts`.

## 7. Перевірка

Раннер — лише Playwright Test, проєкти `unit` і `e2e`.

**unit:**
- `parseSnapshotParams`: 7 допустимих вікон; `14`, `16`, `99999`, `abc`, `''`,
  `015`, `classB=2`, повтор → відмова; без параметрів → 15 / `false`.
- Обробник: 400 `invalid_params` без звертання до `connect`; `windowSeconds` і
  `includeClassB` у відповіді; `diagnostics: null` для `no_api_key`; помилка
  `disconnected` несе лічильники й не несе суден.
- `buildSubscription`: один тип без опції, рівно два з `includeClassB`.
- Збирач: `messages`, `rejected`, `byType`, `connectMs` за підставленим годинником;
  підтвердження підписки не рахується.
- Перетворювач класу B — за живим зразком; ті самі межові випадки валідації.
- `fetchSnapshot`: параметри в URL; `abort` → `'cancelled'`.
- Підпис: 15 / 120 / 300 с; з класом B, з лімітом і обома.
- Рядок діагностики: з'єднання відкрите / не відкрите, успіх / помилка.
- Конфігурація: `SNAPSHOT_WINDOW_SECONDS ∈ SNAPSHOT_WINDOW_OPTIONS`.

**e2e** (підміна `GET /api/snapshot`):
- без дотику до налаштувань запит іде з `window=15&classB=0` (клієнт шле
  параметри завжди; сервер без них дає те саме — перевіряє unit); тести R2 без
  змін у твердженнях. _Єдина правка в `tests/e2e/snapshot.spec.ts`_ — шаблон
  `page.route`: glob `**/api/snapshot` у Playwright закріплений `$` і запит із
  рядком параметрів не перехопив би, тож він стає предикатом за `pathname`;
- повзунок на 2 хв → у запиті `window=120`; підпис «знімок за 120 с»;
- прапорець → `classB=1`; підпис із « · із малими суднами (клас B)»;
- «Скасувати» → запит обірвано, повідомлення «Завантаження скасовано», суден
  немає, кнопка знову «Завантажити справжні позиції»; тест R2 «кнопка
  заблокована» переписаний: у `loading` замість неї «Скасувати»;
- «Докладно» закритий за замовчуванням, розкривається кліком.

Ворота готовності — `npm run verify:full`.

## 8. Порядок робіт

Кожен крок закінчується зеленим `npm run verify`.

1. Конфігурація й `parseSnapshotParams`; 400 `invalid_params`.
2. Діагностика в збирачі й відповіді.
3. Клієнт: `fetchSnapshot` з параметрами й скасуванням; стан `cancelled`, кнопка
   «Скасувати».
4. Повзунок, прапорець, «Докладно», доповнення підпису.
5. Клас B: скрипт зразка → запуск власником → перетворювач і підписка. Останнім,
   щоб не блокувати П-1 і П-3.
6. `npm run verify:full`.

## 9. Ризики

- **Класу B у протоці може не бути** — у вимірах їх там не було. Перемикач
  чесний: він розширює підписку, а не обіцяє судна.
- **Вікно 5 хв** — довго; саме тому «Скасувати» входить у цей обсяг.
- **Зразок класу B може відрізнятися за полями** від `PositionReport` — тоді
  перетворювач отримує окрему гілку розбору, а не спільну; рішення — після
  зразка.
