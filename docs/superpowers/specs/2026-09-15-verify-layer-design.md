# Шар перевірки (verify layer) + Stop-гейт Claude Code

**Дата:** 2026-09-15
**Статус:** дизайн на вичитку
**Стосується:** методу роботи (SPRINT-01, Частина Б), не функціональності застосунку

---

## 1. Властивість, заради якої це будується

Одна, і решта документа їй підпорядкована:

> Неможливо заявити «зроблено», поки щось насправді зламане, і неможливо зробити зелено, послабивши перевірку замість того, щоб полагодити причину.

З цього випливають два наслідки, які й формують дизайн:

- **Статус з'являється лише там, де є відтворюваний факт.** Перевірка, яку команда може повторити без моделі, дає статус. Judgement моделі — не дає ніколи; він lead, тобто називає ризик, ще не оформлений у правило.
- **Пропущене ніколи не читається як пройдене.** Відсутність передумови (браузера, бінарника) не говорить про код нічого — і має виглядати інакше, ніж зелене й ніж червоне.

## 2. Межі

**Будуємо:** реєстр перевірок, п'ять статусів, два рівні, кеш за вмістом, три власні структурні перевірки, три хуки Claude Code.

**Свідомо не будуємо, з причинами:**

| Не будуємо | Чому саме тут |
| --- | --- |
| Рачети + `baselines/*.json` | Рачет існує для боргу, який сьогодні не виправити. У репозиторії два файли коду й нуль винятків: baseline засіявся б порожнім масивом, а двобічна звірка порівнювала б порожнє з порожнім. Додається тоді, коли з'явиться перший справжній виняток, вартий датування |
| `verify:ci` і CI parity | CI не існує й не передбачений: «localhost only, loopback only, nothing deployed». Скрипт охороняв би неіснуючий pipeline |
| `memo` / docs-drift | Потрібна згенерована таблиця, варта захисту. З'явиться разом із розділом «Перевірка» в `CLAUDE.md` — після того, як реєстр стабілізується |
| `selfcheck` | Має сенс, коли в шарі буде логіка, варта тестів. Заводиться одночасно з першими unit-тестами шару |

`memo` і `selfcheck` — відкладені, не відкинуті; обидва потребують того, чого ще немає.

## 3. Архітектура

### 3.1 Реєстр — дані, не скрипти

Кожна перевірка — рядок у `scripts/verify/registry.mjs`:

```js
{
  id: 'typecheck',
  tier: 'fast',
  cmd: 'npx tsc -p tsconfig.json --noEmit',
  needs: [],              // id передумов
  after: [],              // id перевірок, від яких залежить
  proves: '…',
  blindSpot: '…',
}
```

Два правила для прози:

- `proves` має бути **спростовним**: якщо жодна можлива поведінка `cmd` не зробила б це речення хибним — рядок декоративний, і його треба видалити.
- `blindSpot` **не має права бути вужчим** за те, що перевірка насправді пропускає. Занижений `blindSpot` небезпечніший за відсутній, бо створює хибну впевненість.

### 3.2 П'ять статусів

| Статус | Значення | Блокує |
| --- | --- | --- |
| `PASSED` | Виконалася, проблем не знайшла | ні |
| `FAILED` | Передумова була, перевірка виконалася, знайшла проблему | так |
| `SKIPPED` | Передумови справді не було (немає браузера, бінарника, 0 тестів). **Про код не говорить нічого** | лише за `--no-skip` |
| `NOT_RUN` | Перевірка з `after:` не запускалась, бо впала та, від якої вона залежить | так |
| `UNRUNNABLE` | Сама перевірка не змогла запуститися: `spawn ENOENT`, exit 127, нерозбірний вивід | так |

Розрізнення `FAILED` / `UNRUNNABLE` — не педантизм. Повідомити «перевірка впала», коли вона ніколи не могла запуститися, означає стверджувати щось про код, який ніхто не перевіряв. Обидві помилки — і `FAILED`, і `PASSED` — тут однаково брехливі.

**Окремий випадок, специфічний для цього спринту:** Playwright із нульовою кількістю знайдених тестів дає `SKIPPED` з причиною «0 тестів написано», а **не** `PASSED`. «Пройшло 0 тестів» не доводить нічого, і подавати це зеленим — рівно та поведінка, яку шар має ловити.

### 3.3 Два рівні

| Рівень | Склад | Коли |
| --- | --- | --- |
| `fast` | все, що не потребує браузера, демона, мережі | кожен хід агента; ціль — секунди |
| `full` | `fast` + `build` + `e2e` | перед передачею людині й перед checkpoint |

Скрипти:

```
npm run verify              # fast
npm run verify:full         # fast + full
npm run verify:checkpoint   # full + --no-skip
```

`verify:checkpoint` — місцевий відповідник `verify:ci` з брифу. У проєкті без CI роль «моменту, коли пропуск недопустимий» відіграє checkpoint: SPRINT-01 вимагає записати, «які команди виконані й з яким результатом». Під `--no-skip` пропуск стає провалом, тож у запис не може потрапити зелене, під яким половина не бігла.

### 3.4 Свіжість — за вмістом, ніколи за часом

`scripts/verify/hash.mjs` → `sourceHash(root)` → `{hash, fileCount}`.

- Джерело списку: `git ls-files -c -o --exclude-standard -z`, звужене до префіксів, що реально годують перевірки: `app/`, `tests/`, `scripts/verify/`, `.claude/hooks/`, `package.json`, `package-lock.json`, `tsconfig.json`, `next.config.ts`, `eslint.config.mjs`, `playwright.config.ts`. `.claude/hooks/` входить тому, що зміна хука змінює поведінку перевірки — кеш має протухати й від неї.
- `-z` обов'язковий: без нього git лапкує й екранує шляхи зі спецсимволами, і список тихо розсинхронізується з диском.
- Хеш рахується від **вмісту**, не від `mtime` і не від «git status чистий».

Причина категорична: закомічений хід лишає чисте дерево, тож «дерево чисте» видало б зелене вже зламаному коду. `mtime` ламається від `git checkout`, `touch` і відновлення з архіву.

`--reuse-if-fresh`: якщо поточний хеш збігається з останнім записаним `PASS` — передрукувати кешований вердикт замість повторного прогону.

**Кеш тут виконує другу роботу — злиття паралельних перевірок.** Три одночасні редагування дають один підсумковий хеш, тож перший прогін відповідає на всі три. У найгіршому разі двоє стартують разом і один прогін (~0,9 с) витрачається дарма, але результат завжди правильний, бо адресований вмістом, а не порядком. Лок лишається оптимізацією, а не умовою коректності — що істотно, бо документація Claude Code **не обіцяє** ні локів, ні порядку, ні обмеження конкурентності хуків.

## 4. Реєстр перевірок

### Рівень `fast`

| id | cmd | proves | blindSpot |
| --- | --- | --- | --- |
| `typecheck` | `tsc -p tsconfig.json --noEmit` | Кожен `.ts`/`.tsx` проєкту компілюється під `strict` із типами Next | Нічого про поведінку в рантаймі. `skipLibCheck: true` ховає помилки чужих `.d.ts`. Leaflet не виконується, тож звернення до `window` на рівні модуля тут скомпілюється успішно |
| `lint` | `eslint .` | Жоден файл не порушує правила `eslint-config-next` і базові правила TS | Стиль і статичні шаблони, не логіку. Правило, якого немає в конфігу, не порушується за визначенням |
| `unit` | `playwright test --project=unit` | Чисті функції поводяться як задано — для написаних випадків | Ні браузера, ні DOM, ні Leaflet. Про рендер і карту не говорить нічого. Випадок, якого ніхто не написав, не покритий |
| `no-ref-imports` | `node scripts/verify/checks/no-ref-imports.mjs` | Жоден файл застосунку чи тестів не має `import`/`require` із `reference/` — ні в рантаймі, ні на рівні типів | Тільки статичні літерали шляхів. Шлях, зібраний обчисленням у рантаймі, невидимий |
| `no-secrets` | `node scripts/verify/checks/no-secrets.mjs` | Жоден файл, що потрапляє до передачі, не містить рядків, схожих на ключ або токен | Порівняння за шаблонами: секрет у незвичному кодуванні або розбитий на рядки невидимий. Ігноровані git-ом файли не скануються — і не передаються |
| `deps-allowlist` | `node scripts/verify/checks/deps-allowlist.mjs` | `package.json` містить лише узгоджений набір; другого тестового раннера й другої бібліотеки карт немає | Тільки прямі залежності. Не доводить, що дозволена залежність узагалі використовується |

Три останні — це «documented-but-unenforced» інваріанти **цього** репозиторію, а не перенесені з чужого проєкту. Заборона `import` із `reference/` записана у двох `CLAUDE.md` тричі й досі не стережеться нічим; заборона секретів у переданих файлах має прямий наслідок на прийманні; критерії B-01 і B-07 прямо вимагають відсутності зайвих залежностей і другого раннера.

**`no-secrets` не друкує знайдене.** Звіт дає `file:line` і маркер типу, ніколи сам рядок — інакше перевірка порушувала б правило, яке охороняє.

### Рівень `full`

| id | cmd | after | proves | blindSpot |
| --- | --- | --- | --- | --- |
| `build` | `next build` | `typecheck` | Застосунок збирається і серверний рендер не звертається до `window` на рівні імпорту — запобіжник SSR для Leaflet | Нічого не натискає. Карта, що вийшла сірою, збірку проходить |
| `e2e` | `playwright test --project=e2e` | `build` | Поведінки вибору з B-07 виконуються у справжньому chromium проти dev-сервера | **Рух не перевіряє** — перевірка руху з керованим часом належить R3. Тайли заблоковані, тож про справжні зображення карти не говорить нічого |

Рядок `blindSpot` для `e2e` — дослівна вимога SPRINT-01: «Рух цього тижня перевіряється візуально; автоматична перевірка руху з керованим часом — завдання релізу R3, і в записі checkpoint це так і записується».

### Передумови

`PRECONDITIONS` — мапа `id → {describe, probe}`. Проба відповідає **лише** на «чи можу я взагалі запуститися», ніколи на «чи пройшло».

| id | Проба | Наслідок за відсутності |
| --- | --- | --- |
| `node-modules` | `node_modules/` існує | усі рядки → `SKIPPED` |
| `playwright-pkg` | `@playwright/test` резолвиться | `unit`, `e2e` → `SKIPPED` |
| `playwright-browser` | бінарник chromium є в кеші | `e2e` → `SKIPPED` |

## 5. Раннер

`scripts/verify/run.mjs`.

**CLI:** `--tier fast|full`, `--no-skip`, `--only a,b`, `--reuse-if-fresh`, `--json`, `--timeout-ms`.

**Виконання:** кожен `cmd` через `/bin/sh` із кореня репозиторію, з таймаутом, безпечним для групи процесів (вбивати групу, не лише лідера — інакше `next build` лишає дітей).

**Вивід:** JSON-звіт у `.verify/last-run.json`; у термінал — таблиця, що поважає TTY і `NO_COLOR`.

**Коди виходу:** `0`, якщо нічого блокувального; `1` інакше.

```js
isBlocking(status, noSkip) {
  if (status === 'PASSED') return false;
  if (status === 'SKIPPED') return noSkip;
  return true;             // FAILED, NOT_RUN, UNRUNNABLE
}
```

## 6. Хуки

Механіка нижче **звірена з чинною документацією** (`code.claude.com/docs/en/hooks`), не з пам'яті й не з брифу. Бриф у цьому місці помилявся — див. §9.

### 6.1 `.claude/hooks/node.sh`

POSIX `sh`, **самі лише вбудовані команди** — без `dirname`, `sed`, `ls`: ворожий або порожній `PATH` не має ламати саме визначення шляхів.

Обов'язки: знайти інтерпретатор Node (спершу той, чий major збігається з `.nvmrc` — тут 24), експортувати `PATH` разом із `node_modules/.bin`, і за неможливості — **впасти відкрито й голосно**: `{"systemMessage": "…"}`, ніколи тихий ненульовий вихід.

Причина: хук не успадковує середовище інтерактивного shell. Голий `npm run x` у хуку інакше повідомить `UNRUNNABLE` із неправильної причини — і це найгірший різновид брехні, бо виглядає як висновок про код.

### 6.2 `.claude/hooks/edit-check.mjs` — подія `PostToolUse`

Матчер `Edit|Write` (перевірено: форма з `|` — це список точних збігів, регістрозалежний; `MultiEdit` із брифу тут мертвий, такого інструмента немає).

Шлях файлу береться з `tool_input.file_path` — єдиного задокументованого й гарантованого поля для обох інструментів.

Алгоритм:

1. Не код (`.ts`, `.tsx`, `.mjs`, `.js`) або шлях під `reference/`, `.next/`, `node_modules/` → тихий вихід `0`.
2. `eslint <file>` — звуження справжнє, перевірка файлова.
3. `typecheck` — **весь проєкт**, із ключуванням за хешем. Звуження тут фіктивне: `tsc --noEmit <file>` дає `TS5112` і не завантажує `tsconfig.json`, тобто втрачає `strict`, `jsx` і типи Next. Звужується **звіт**, не перевірка: спершу помилки у щойно відредагованому файлі, далі лічильник помилок деінде. Зламане в іншому файлі не ховається — воно найдорожче.
4. Вивід: `{"hookSpecificOutput": {"hookEventName": "PostToolUse", "additionalContext": "…"}}`, вихід `0`.

**Цей шар не блокує — і не за моїм вибором.** Документація: для `PostToolUse` — `Can block? No`, інструмент уже виконався. Це збігається з потрібною поведінкою: посеред рефакторингу код законно зламаний, і змушувати «чинити» файл 1 із 3 було б шкідливо. Шар дає **lead**, статус дає лише §6.3.

Одне об'єднане спрацювання замість двох окремих хуків із брифу: обидві перевірки разом дають ~1,5 с, і другий запуск Node не окупається. Відхилення свідоме.

### 6.3 `.claude/hooks/stop-gate.mjs` — подія `Stop`

1. Прочитати stdin JSON із коротким запобіжником на таймаут. Зависле читання не має вішати хід — але й **не має тихо вважатися порожнім**: порожнє читання загубило б `prompt_id` і вимкнуло лічильник блокувань.
2. Якщо `stop_hook_active === true` → вихід `0`. Прапорець означає строго «Claude продовжує, бо Stop-хук раніше заблокував зупинку».
3. Запустити `node scripts/verify/run.mjs --tier fast --reuse-if-fresh --json`.
4. **Раннер не дав придатного результату** (падіння, таймаут, нерозбірний звіт) → `{"systemMessage": "ГЕЙТ НЕ ВІДПРАЦЮВАВ — не заявляй успіх"}`, вихід `0`. Fail open, але голосно.
5. **Зелено** → скинути лічильник. Якщо був бодай один `SKIPPED` → `systemMessage`, який вимагає сказати це вголос у відповіді. «Зелено, але X пропущено» — інше твердження, ніж «зелено».
6. **Червоно** → таблиця провалів (статус + id + коротка причина), обрізана **за байтами через `Buffer`**, не за довжиною рядка. Тут це не теоретично: весь текст проєкту українською, тобто двобайтовий, і наївний `slice` ріже літеру навпіл. Далі — `{"decision": "block", "reason": "…"}` і вихід `2`.
7. **Межа livelock:** лічильник на `prompt_id` у `.verify/gate-counter/`, максимум 2 поспіль. Далі гейт перестає блокувати й натомість вимагає відкрити відповідь явною заявою «досі червоно, ось що падає». Claude Code має власну межу у 8 блокувань — наша суворіша й спрацьовує раніше.
8. **Запис перед `process.exit`** — циклом за байтовим зсувом у сирий fd, із повтором на `EAGAIN`. Асинхронний запис у pipe обрізається синхронним `process.exit` одразу після нього; це різниця між тим, чи причина блокування дійде до моделі, чи прийде порожньою.

### 6.4 Вмикання

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/node.sh \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/edit-check.mjs",
        "timeout": 120
      }]
    }],
    "Stop": [{
      "hooks": [{
        "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/node.sh \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/stop-gate.mjs",
        "timeout": 300
      }]
    }]
  }
}
```

Таймаути задані явно, бо дефолт command-хука — 600 с, а гейт, що висить десять хвилин, зламаний.

Живе у `.claude/settings.json` (передається). Ключ `hooks` між рівнями налаштувань **зливається**, тож `settings.local.json` проєктні хуки не затре.

Власний peer-діапазон `eslint-config-next` (`>= 9`) формально дозволяє 10, але два плагіни, які він тягне залежностями — `eslint-plugin-react@^7.37` (`^3 \|\| … \|\| ^9.7`) і `eslint-plugin-jsx-a11y@^6.10` (`… \|\| ^9`) — **не заявляють `^10`**. Тобто 9.x тут не обережність, а єдиний варіант без peer-конфлікту |
| `eslint-config-next` | 16.3.5 | точно під `next@16.3.5` |
| `@playwright/test` | 1.63.x | рядки `unit` і `e2e`; передбачений B-07 |

**Це свідомий виняток** із правила «жодних зайвих залежностей», і в checkpoint він записується як виняток із обґрунтуванням: усі три — інструменти перевірки, не залежності застосунку; `@playwright/test` прямо передбачений B-07. Жодна не потрапляє до коду, що виконується в браузері.

Другий тестовий раннер **не додається**. Юніт-тести виконує Playwright Test окремим проєктом `unit` без браузера — критерій B-07 «інших тестових фреймворків немає» лишається виконаним. Це й стереже рядок `deps-allowlist`.

Завантаження браузера Playwright довге — запускається у фоні, як вимагає `CLAUDE.md`.

## 9. Відхилення від вихідного брифу

| Місце брифу | Тут | Причина |
| --- | --- | --- |
| `hookSpecificOutput: {hookEventName: 'Stop', decision, reason}` | `{"decision": "block", "reason": …}` **верхнього рівня** + exit 2 | За чинною документацією для `Stop` `decision`/`reason` — поля верхнього рівня; `hookSpecificOutput.additionalContext` — окремий, *неблокувальний* канал. Форма з брифу зблокувала б нічого, тихо. Бриф сам велів це звірити — вказівка виявилася правильною |
| `edit-lint.mjs` + `batch-typecheck.mjs` окремо | один `edit-check.mjs` | ~1,5 с разом; другий запуск Node не окупається |
| Матчер `Edit\|Write\|MultiEdit\|NotebookEdit` | `Edit\|Write` | `MultiEdit` не існує; ноутбуків у проєкті немає |
| Рачети, CI parity | не будуються | §2 |

Не перевірено й тому не використано: чи спрацьовує подія `PostToolBatch` для пакета з одного виклику. Якщо так — вона спростить §6.2, прибравши потребу в ключуванні за хешем для злиття. Дизайн від неї **не залежить**; це можливе спрощення потім, записане тут, щоб не загубитися.

## 10. Запис у checkpoint

Шар передається клієнтові й описується в `docs/checkpoints/CHECKPOINT-0N.md`:

1. Команди `verify`, `verify:full`, `verify:checkpoint` — що кожна запускає.
2. Таблиця `proves` / `blindSpot` — прямо відповідає на питання тижня «що доводять тести вибору і **чого не доводять**».
3. Три нові залежності як свідомий виняток, із обґрунтуванням із §8.
4. Явно: рух перевірено **візуально**, не тестом; автоматична перевірка руху — R3.
5. Результат останнього прогону `verify:checkpoint` — із назвами пропущених рядків, якщо такі були.

**Залежність:** `docs/checkpoints/TEMPLATE.md`, на який посилається `CLAUDE.md`, ще не існує — тека порожня. Запис має лягти в шаблон, коли той з'явиться; до того часу структура вище є пропозицією, не готовим записом.

## 11. Чого цей шар не доводить

Розділ обов'язковий: шар, який не називає власних сліпих плям, сам стає тим, від чого мав би берегти.

- **Нічого візуального.** Сіра карта, картка, що роз'їхалася, значок під неправильним кутом — усе це проходить усі вісім рядків. SPRINT-01 покладає це на очі, і так і лишається.
- **Нічого про рух.** Свідомо, до R3.
- **Нічого про формати з ТЗ**, поки хтось не напише unit-тест на кожен. Порожня тека `tests/unit/` дає `SKIPPED`, а не `PASSED` — саме щоб ця діра була видима.
- **Нічого про судження моделі.** Findings Клода лишаються lead: хук їх не рахує й не може перевірити. Це припис у тексті блокування, а не механізм — і в цьому документі це сказано прямо, щоб ніхто не вважав інакше.
- **Нічого про те, чого немає в реєстрі.** Реєстр — межа того, що шар узагалі бачить.
