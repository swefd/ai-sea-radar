## 2. Стан на момент рішення: що виміряно до першої правки

### 2.1. `.gitignore` зараз не захищає того, що B-08 вимагає захистити

У робочому дереві лежить незакомічена правка, яка послабила `.env*` до `.env`.
Наслідок виміряний, а не передбачений:

```
$ for f in .env .env.local .env.production.local .env.example; do
    printf '%-26s ' "$f"; git check-ignore -q "$f" && echo IGNORED || echo "NOT IGNORED"
  done
.env                       IGNORED
.env.local                 NOT IGNORED   ← потрапив би в коміт
.env.production.local      NOT IGNORED   ← потрапив би в коміт
.env.example               NOT IGNORED   ← так і треба, його комітять
```

Тобто рядок, що стоїть у дереві, робить протилежне до критерію B-08 «`.env.local` не
в `git ls-files`». `.env.example` теж не відповідає узгодженому значенню `:24`: у ньому
`aisstream_api_key=your_api_key_here` — інший регістр і зі значенням, тоді як завдання
фіксує рядок `AISSTREAM_API_KEY=` без значення.

У корені лежить `.env` на 58 байт зі справжнім ключем (повідомлено людиною). Агент його
не читав і не читає — §3.5.

### 2.2. Три джерела про підписку розходяться; правда — `APIKey`

| Джерело | Рядок | Дослівно |
| --- | --- | --- |
| `reference/aisstream-typescript-example/client.ts` | `:11` | `Apikey: "YOUR API KEY",` |
| `reference/ais-message-models/models/SubscriptionMessage.ts` | `:17` | `'aPIKey': string;` |
| той самий файл | `:26`–`:27` | `"name": "aPIKey",` / `"baseName": "APIKey",` |
| aisstream.io/documentation | — | `"APIKey": "<YOUR_API_KEY>",` |
| `docs/tasks/SPRINT-02.md` | `:23` | `{ APIKey, BoundingBoxes: … }` |

Розходження **одне, не два**: `aPIKey` — властивість згенерованого класу, і той самий
файл рядком нижче сам оголошує, що на дроті вона зветься `APIKey`. Довідка
`reference/ais-message-models/CLAUDE.md` про це попереджає: «The wire JSON uses the
`baseName` from that map… Read the `baseName` column, not the property names.»
Реально розходиться лише офіційний приклад, і його власна довідка наказує звірятися з
живою документацією, а не з ним.

**Пишемо `APIKey`.** Пари в `BoundingBoxes` — `[lat, lon]`, як у завданні й документації.

### 2.3. `time_utc` немає в жодному джерелі, крім завдання

```
$ grep -rn "time_utc" reference/ais-message-models/
$ echo $?
1        ← жодного збігу в усіх 46 моделях
```

`PositionReport.ts:110`–`:111` натомість має `"name": "timestamp"` / `"baseName":
"Timestamp"`, і це `'timestamp': number` (`:28`) — **число**, секунда AIS, не рядок.
Жива документація `time_utc` теж не друкує: у прикладі `MetaData` стоять `MMSI`,
`ShipName`, `Latitude`, `Longitude` — з великої літери, тоді як `SPRINT-02.md:25` пише
`latitude`, `longitude` з малої.

`MetaData` у моделі типізований `any` (`AisStreamMessage.ts:27`), тобто згенеровані
моделі про його вміст не кажуть нічого; `ShipName` не зустрічається в `models/` ніде.

**Це не розв'язується сперечанням документів.** Завдання визнає те саме тим же рядком
`:25`: «Регістр і точний набір полів підтверджуються збереженим зразком; перетворювач
пишеться за зразком». Саме тому B-10 стоїть **перед** B-11, а B-09 віддає повідомлення
сирим: єдиний спосіб дізнатися форму — отримати її.

### 2.4. `ws` не потрібен — вимір, не обережність

```
sec-websocket-extensions: permessage-deflate; client_max_window_bits
```

Заголовки рукостискання вбудованого `WebSocket` у Node 24.21, зняті локальним
HTTP-сервером. Клієнт **сам пропонує** стиснення. Офіційний приклад тягне залежність
`ws` рівно заради `perMessageDeflate: true` (`client.ts:6`) — нам це не потрібно.

Наслідок: **нових залежностей нуль**, рядок `deps-allowlist` не чіпається, правило «no
extra dependencies» не порушується і не потребує нового винятку.

### 2.5. Бінарні фрейми — пастка, якої немає в жодній довідці

Локальний WS-сервер, що шле бінарний фрейм з UTF-8 JSON (саме так, як описує
документація: «The server sends binary WebSocket frames containing UTF-8 JSON»),
прочитаний вбудованим клієнтом Node 24.21:

```
binaryType за замовчуванням: blob
typeof event.data      : object
constructor            : Blob
JSON.parse(event.data) : "THREW: SyntaxError"
```

**`JSON.parse(event.data)` кидає** — рівно той рядок, що стоїть в офіційному прикладі
(`client.ts:18`). `Blob` синхронно не читається. Лікується одним рядком
`ws.binaryType = 'arraybuffer'` **до** підписки на події.

Це вбило б B-09 мовчки: з'єднання відкрите, фрейм прийшов, розбір упав. Жодна з трьох
довідок про це не попереджає, бо жодна не бігла на Node 24 без `ws`.

### 2.6. Що ще каже жива документація і чого немає в довідках

Дослівно зі сторінки:

- «Send one complete JSON subscription within **3 seconds**» — спізнення закриває з'єднання.
- «The server sends binary WebSocket frames containing UTF-8 JSON.»
- «Direct browser connections are not permitted; proxy only the information your clients
  need from your own server.» — тобто вимога «тільки з сервера» (`:23`) не наша
  обережність, а умова джерела.
- «Each accepted subscription or replacement returns a `SubscriptionConfirmation`» з полем
  `Message.CompressionEnabled`.

Останнє **суперечить** `SPRINT-02.md:23` («Підтвердження підписки джерело не надсилає») — §4.2.

## 3. Ухвалені рішення: секрет (B-08)

### 3.1. Порядок незмінний: захист → перевірка на фіктивному файлі → справжній ключ

`SPRINT-02.md:84` задає його дослівно, і він не переставляється. Причина не церемоніальна:
захист, доданий після того, як ключ уже лежить у дереві, не перевіряється — неможливо
відрізнити «правило працює» від «файлу просто не торкалися».

### 3.2. `.gitignore` — `.env*` із винятком

```
.env*
!.env.example
```

Повернення до стандарту Next.js, а не нововведення: §2.1 показує, що послаблення до
`.env` лишало два файли з ключем незахищеними. Виняток для `.env.example` git розуміє
штатно.

Доводиться не оком, а командою — `git check-ignore` по тих самих чотирьох іменах, що в
§2.1, з очікуваним «перші три IGNORED, `.env.example` — ні».

### 3.3. `.claude/settings.json` — три правила, і це ВИБІР, а не обмеження

```json
"deny": ["Read(./.env)", "Read(./.env.local)", "Read(./.env.*.local)"]
```

`SPRINT-02.md:84` стверджує: «одним глобом з винятком `.env.example` deny не
виражається». **Для CLI 2.1.278 це неправда** — перевірено в первинному джерелі,
`code.claude.com/docs/en/permissions`, дослівно:

> «A deny or ask pattern that starts with `!` is a gitignore negation. It carves the
> paths it matches out of the `path` or `./path` rules listed before it. In one settings
> file's `deny` list, `Read(*.env)` followed by `Read(!sample.env)` blocks every file
> whose name ends in `.env` at any depth, except files named `sample.env`. A `!` rule
> listed first carves nothing out.»

Тобто `Read(./.env*)` + `Read(!.env.example)` виразилося б. Той же документ дає три
обмеження негації: вона має стояти **після** правила, діє лише в межах **одного** файлу
налаштувань, і не читається відносно якорів `/`, `~/`, `//`.

**Обираємо все одно явний перелік** — з причини, не з незнання: глоб із негацією
**відкрив би `.env.example` на читання**, а нам цього не потрібно. Агент цей файл
створює, а не читає. Явний перелік вужчий і збігається з буквою завдання.

Різниця між застарілим рядком завдання і виміряною реальністю записується сюди й у
checkpoint; сам `docs/tasks/SPRINT-02.md` не редагується — §7.

### 3.4. Модуль ключа — юніон, не рядок і не виняток

`src/shared/config/aisstream.ts`, реекспорт через наявний `src/shared/config/index.ts`:

```ts
type ApiKeyState =
  | { status: 'missing' }
  | { status: 'present'; apiKey: string };
```

Порожній рядок і рядок із самих пробілів → `missing`. Юніон, а не `string | null`, з
однієї причини: `no_api_key` у B-09 стає **гілкою розбору**, а не перевіркою на
порожнечу в трьох місцях. Критерій B-08 «повертає "ключ відсутній" без винятку»
виконується формою типу, а не домовленістю.

Читається **тільки** на сервері. Змінна без префікса `NEXT_PUBLIC_` до клієнтського
бандла не потрапляє — але це властивість Next.js, а не наша перевірка, і §6 каже, чим
саме вона доводиться.

### 3.5. Ключ переносить людина, не агент

Ключ зараз у `.env` (§2.1). Перенести його в `.env.local` і видалити `.env` — дія
людини. Агент `.env` не читав і не читатиме.

Обидва файли Next.js читає, тож ключ у двох місцях — це два периметри замість одного,
і другий не названий у жодному правилі.

### 3.6. Названа межа: deny не покриває `grep -r`

Той самий документ, дослівно:

> «Read and Edit deny rules apply to Claude's built-in file tools, to file commands
> Claude Code recognizes in Bash, such as `cat`, `head`, `tail`, `sed`, and `tee`… They
> don't apply to a command that reads files without naming them, such as `grep -r pattern
> .` run from the directory that holds the file, or to arbitrary subprocesses that read
> or write files indirectly, like a Python or Node script that opens files itself.»

І про решту шляхів:

> «Claude makes a **best-effort** attempt to apply `Read` rules to all built-in tools
> that read files like Grep and Glob, to `@file` mentions in your prompts…»

Отже правило permissions **сильніше** за рядок у `CLAUDE.md` — воно виконується
харнесом, а не залежить від дисципліни агента; рівно та різниця, яку `SPRINT-02.md:108`
просить зрозуміти до кінця тижня. Але воно **не** OS-рівневий бар'єр: рекурсивний grep
із кореня проєкту й будь-який Node-скрипт його обходять.

Межа названа тут, повториться в checkpoint і не замовчується. `.gitignore` і `CLAUDE.md`
захистом не рахуються взагалі — так каже `SPRINT-02.md:84`, і §2.1 показує, чому:
`.gitignore` тихо послабили, і ніхто цього не помітив.

## 4. Ухвалені рішення: reader і endpoint (B-09)

### 4.1. П'ять модулів, і лише один знає слово WebSocket

```
app/api/snapshot/route.ts           тонкий: літеральні runtime/dynamic + реекспорт GET
src/_app/api-routes/snapshot.ts     адаптер: юніон результату → HTTP-статус і тіло
src/shared/api/aisstream/reader.ts  ЧИСТА логіка: строк, єдине завершення, прибирання
src/shared/api/aisstream/connect.ts ЄДИНИЙ модуль із WebSocket
src/shared/config/aisstream.ts      ключ (§3.4) + константи вікна
```

Розкладка взята зі скіла `feature-sliced-design`, розділ Next.js App Router: Route
Handler лишається тонким, реалізація живе в `_app/api-routes/`, транспорт без доменних
правил — у `shared/api`.

Правило 4-5 («no business logic in shared») **не порушене**: B-09 свідомо не розбирає
формат повідомлення. У `shared/api` лежить транспорт, домену там немає. Перетворювач
сяде в `entities/vessel` на B-11 — після зразка, не раніше.

`export const runtime = 'nodejs'` і `export const dynamic = 'force-dynamic'` стоять
**літералами в `route.ts`**: Next читає їх статичним аналізом сегмента, і реекспортом
вони не приїдуть. Друга константа не декоративна — знімок не можна віддати з кешу.
Доводиться збіркою (§6).

### 4.2. Межа `connect` — джерело подій як параметр

```ts
type Connect = (handlers: {
  onOpen: () => void;
  onMessage: (text: string) => void;
  onError: () => void;
  onClose: () => void;
}) => { send: (text: string) => void; close: () => void };
```

Reader приймає `connect`, годинник і строк — і не знає слова WebSocket. Тест подає свій
`connect`, смикає обробники руками й рухає час: ні сокета, ні сервера, ні очікування 15
секунд. Це дослівна вимога `SPRINT-02.md:28` («Джерело подій і годинник — параметри
збирача, щоб тести подавали повідомлення й рухали час без мережі»), винесена на B-09,
щоб B-12 успадкував готову межу й змінив лише логіку накопичення.

Відкинуті альтернативи:

- **Підмінний клас WebSocket.** Тест мусив би вдавати весь браузерний API — `readyState`,
  `binaryType`, `addEventListener`, `CloseEvent`. Підмінка розходиться з оригіналом
  мовчки, і зелений тест проти невірної підмінки — це зелене, яке нічого не доводить.
- **Локальний WS-сервер у тестах.** Працює (ним зняті виміри §2.4 і §2.5), але робить
  час справжнім: тест на строк 15 с бігав би 15 секунд, і «керований час» із завдання не
  виходить. Лишається інструментом разового виміру, не формою сюїти.

Бойовий `connect.ts` — єдине місце, де живуть три факти з §2:

1. **`ws.binaryType = 'arraybuffer'` до підписки на події** (§2.5). Без цього рядка
   розбір падає на першому ж фреймі.
2. **Підписка першою дією в `onOpen`** — 3 секунди за документацією (§2.6).
3. **`permessage-deflate` не налаштовується** — клієнт пропонує його сам (§2.4).

Поле ключа в підписці — `APIKey` (§2.2). Бокс — `[[[50.75, 0.95], [51.25, 1.95]]]` з
наявного `DOVER_STRAIT_REGION`; фільтр — `['PositionReport']`.

**Перше отримане повідомлення віддається як є, навіть якщо це
`SubscriptionConfirmation`.** Завдання каже «перше отримане повідомлення як є», і це
виконується дослівно. Рішення свідоме: §2.6 показав, що `:23` («Підтвердження підписки
джерело не надсилає») розходиться з документацією, і сира відповідь B-09 — єдиний спосіб
**побачити** факт замість того, щоб про нього сперечатися. Фільтрація за
`MessageType === 'PositionReport'` була б уже розбором формату, тобто роботою B-11, яку
завдання забороняє робити до зразка.

### 4.3. Результат завершується рівно один раз

```ts
type ReadResult =
  | { kind: 'message'; raw: unknown }
  | { kind: 'empty' }
  | { kind: 'error'; code: 'connect_failed' | 'provider_error' | 'disconnected' | 'internal' };
```

Одна змінна `settled: boolean` — сторож на **всіх** шляхах виходу. Прибирання
(`close()` + `clearTimeout`) викликається в одному місці, на завершенні, і ідемпотентне.

Пастки названі методом (`SPRINT-02.md:92`) і адресовані саме цією формою: проміс
резолвиться двічі; таймер вікна не очищається; у разі помилки повертаються «вже зібрані»
дані.

`connect_failed` проти `disconnected` розрізняються **фактом надісланої підписки**:
закриття до неї — `connect_failed`, після — `disconnected`. Дослівно за `:29`.

`request.signal` → `abort` закриває сокет і таймер. Скасування — третій результат, не
забутий випадок; `:43` вимагає закриття ресурсів «при завершенні, помилці та скасуванні».

### 4.4. Відповідь — літерали із завдання, без власних формулювань

Успіх: HTTP 200, `{ ok: true, raw, collectedAt }`, де `raw` дорівнює `null` при `empty`.
Помилка: HTTP 502, `{ ok: false, attemptedAt, error: { code, message } }` з фіксованими
текстами з `:29`.

Два свідомі буквалізми:

- **`no_api_key` теж віддає 502**, хоч це конфігурація, а не збій шлюзу. Завдання
  перелічує його серед кодів помилки, а тексти — контракт для тестів B-13; власна
  «розумніша» схема статусів зламала б його.
- Сирий текст помилки провайдера в `message` **не потрапляє** — лише фіксований літерал.
  `:29` вимагає цього прямо, і причина та сама, що в `no-secrets`: діагностика, яка
  друкує чуже, друкує й ключ.

Ключ не логується ніде: живе в одній змінній, іде в `JSON.stringify` підписки й більше
нікуди. Ні в `console`, ні у відповідь, ні в текст помилки.

## 5. Ухвалені рішення: зразок і провенанс (B-10)

`data/samples/position-report.sample.json` — повідомлення у **вихідній** структурі, як
прийшло, без нормалізації.

`data/samples/PROVENANCE.md` пишеться **одразу**, не після. Метод (`:88`) вимагає
розділяти три факти, і провенанс розділить їх явно, бо вони справді різні:

1. з'єднання відкрилося;
2. повідомлення отримано;
3. локальний код перевірено.

«Сокет відкрився» не означає «дані є», і саме це розрізнення тиждень тренує.

Провенанс фіксує також те, що §2.3 і §2.6 лишили відкритим: чи прийшов
`SubscriptionConfirmation` першим; чи є в `MetaData` поле `time_utc` і в якому
написанні; регістр `Latitude` проти `latitude`. Це і є «відмінності від документації»,
яких вимагає `:26`.

**Живий запит виконується тільки після того, як людина прочитала `connect.ts` і модуль
ключа** (`:88`). Причина зрозуміла: перш ніж код торкнеться справжнього ключа, людина
має побачити, що він із ним робить.

Якщо джерело не дало повідомлення або умови не дозволяють зберігати справжнє — діє
запасна гілка `:26`: приклад за схемою з позначкою «не отриманий із живого джерела».
Позначка обов'язкова й у самому файлі, і в провенансі.

Перед комітом зразок проходить `npm run verify` — рядок `no-secrets` просканує його
автоматично як частину периметра передачі.

## 6. Як перевіряємо

| Що доводиться | Чим | Тип |
| --- | --- | --- |
| `.env.local` та `.env.*.local` не в передачі | `git check-ignore` по чотирьох іменах | команда |
| модуль ключа: `missing` / `present` / порожній рядок | юніт-тест, чиста функція, без `process.env` | автомат |
| строк, єдине завершення, прибирання, чотири коди | юніт-тести проти підставного `connect` | автомат |
| `runtime`/`dynamic` прочитані; клієнт не в серверному графі | `npm run build` | автомат |
| без ключа → `no_api_key` | живий `curl` без `.env.local` | руками |
| живий запит → повідомлення / `raw: null` / помилка | живий `curl` з ключем (це вже B-10) | руками |
| deny-правила справді блокують | фіктивний `.env.local`: відмова на ньому, успіх на `.env.example` | руками |
| карта й демонстрація не зламані | `npm run verify:full`, рядок `e2e` (B-07) | автомат |

Ворота готовності — `npm run verify:full`, як каже `CLAUDE.md`. Тільки її зеленість
дозволяє сказати «готово».

Останній рядок таблиці не формальність: B-13 ще попереду, але B-07 має лишитися зеленим
уже зараз, бо цей захід додає серверний код у той самий застосунок.

## 7. Наслідок для документації

Три розходження знайдені й **не виправляються в `docs/tasks/`** — це контракт замовника,

й у checkpoint 03, у розділ «які відхилення від завдання прийняті й чому», якого вимагає
`docs/tasks/ABOUT.md:40`:

1. **`:23` «Підтвердження підписки джерело не надсилає»** — документація каже
   протилежне (§2.6). Наслідок для B-09 прийнятий свідомо (§4.2).
2. **`:84` «одним глобом з винятком deny не виражається»** — для CLI 2.1.278 неправда
   (§3.3). Завдання саме допускало перевірку: «точний синтаксис — за встановленою
   версією CLI». Явний перелік лишається, але як вибір.
3. **`:25` `MetaData.time_utc`** — поля немає ні в моделях, ні в документації (§2.3).
   Не «помилка завдання»: завдання тим же рядком відправляє по правду до зразка. Розв'яже
   B-10, зафіксує провенанс.

Перше й третє — розходження завдання з **джерелом**; друге — з **інструментом**. Різниця
важить: перші два перевіряються повторно будь-коли, третє перевіряється лише живим
запитом і може змінитися з боку AISStream.

## 9. Ризики

**Живе джерело може не дати повідомлення.** Безкоштовний сервіс, і `PROJECT_BRIEF.md:150`
це визнає заздалегідь. Саме тому `empty` — окремий результат, а не помилка, і саме тому
B-10 має задокументовану запасну гілку. Ризик не усувається кодом; він робиться видимим.

**Форма `MetaData` невідома до першого повідомлення** (§2.3). Пом'якшено порядком:
B-09 віддає сире, B-10 зберігає зразок, B-11 пише перетворювач за ним. Якщо зразок
розійдеться з `:25` сильніше, ніж очікувано, це видно **до** написання перетворювача, а
не після.

**`SubscriptionConfirmation` може виявитися першим повідомленням** — і тоді критерій
B-09 «живий запит повертає повідомлення» виконається підтвердженням, а не позицією.
Це прийнято (§4.2) і буде названо в checkpoint прямо, бо мовчазне «повідомлення
отримано» читалося б як «позиція отримана».

**Deny-правила — не OS-рівневий бар'єр** (§3.6). Названо, не закрито.
